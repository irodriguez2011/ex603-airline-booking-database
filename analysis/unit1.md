# Unit 1 Analysis

## Modelling Justification

The five relations in this schema — `passengers`, `airports`, `flights`, `flight_routes`, and `bookings` — use a deliberate mix of surrogate and natural primary keys rather than one rule applied blindly across the board.

For `passengers`, `flights`, and `bookings`, I used surrogate integer keys (`passenger_id`, `flight_id`, `booking_id`) generated by the database itself. None of these entities has an attribute that is guaranteed to be both unique and permanent — names repeat, and even email addresses can change — so a surrogate key avoids ever needing to update a primary key value, which would otherwise ripple through every foreign key referencing it.

`airports`, by contrast, uses a natural key: the three-letter IATA `airport_code` (e.g. `JFK`). This code is already globally unique, stable, and meaningful on its own, so introducing a separate surrogate ID would only add a layer of indirection without solving a real problem. It also keeps `flight_routes` more readable, since every stop is identified by a real airport code instead of an opaque number.

`flight_routes` uses a composite primary key of `(flight_id, stop_sequence)`. This reflects what the row actually represents: not a route in isolation, but the *n*th stop of one specific flight. Neither value alone identifies a row — every flight has a `stop_sequence` of 1 — but the pair together does, the same way a seat isn't uniquely identified by "row 12" or "seat C" individually, but is by both together.

The ON DELETE behaviors were chosen based on how central each relationship is to preserving the platform's history. `bookings.flight_id` and `flight_routes.airport_code` both use `RESTRICT`, because flights and airports are records this platform can't afford to lose silently — a flight with existing bookings represents real revenue, and an airport referenced by active routes is load-bearing reference data. `flight_routes.flight_id` uses `CASCADE` instead, because a route stop has no independent meaning without its flight; if the flight disappears, its stops should too. The most deliberate choice was `bookings.passenger_id`, set to `SET NULL` rather than `RESTRICT` or `CASCADE`. This lets the platform honor an account-deletion request without erasing the booking or its `fare_paid` — the transaction stays in the historical record, just no longer traceable to a specific person.

Finally, I enforced several rules at the database level rather than trusting the application to check them. `CHECK` constraints require a flight's `arrival_time` to come after its `departure_time`, and that `base_fare` and `fare_paid` can never be negative — these are physical and financial impossibilities that should never exist in the data, no matter which script or interface writes the row. `NOT NULL` constraints on fields like `flight_number` and `email` protect against incomplete records that would make a row practically useless. I left more changeable business logic — like whether a specific seat is available, or how a fare is calculated — to the application layer, since those rules shift over time and aren't hard integrity boundaries the way the constraints above are.

## Reflection

The clearest open decision in this design is the ON DELETE behavior on `bookings.passenger_id`. A different designer could reasonably have chosen `RESTRICT`, refusing to delete a passenger at all while bookings exist, on the grounds that booking and revenue records should be permanently traceable to the person who created them. That's a defensible, even common, choice for financial systems.

I chose `SET NULL` instead because of how this platform will actually be read and written. Reads against `bookings` are overwhelmingly aggregate — revenue per flight, bookings per flight, booking frequency per passenger — queries that group and sum `fare_paid` without needing every row to still resolve to a live passenger. Writes against `passengers`, meanwhile, will occasionally include deletions driven by account closures, not just routine signups. `RESTRICT` would block those deletions for as long as any booking history exists, which for an active passenger is effectively forever, making the constraint nearly impossible to honor in practice. `SET NULL` keeps the aggregate reads accurate, since `fare_paid` and `flight_id` are untouched, while still letting the deletion write succeed. The cost is that a small number of historical bookings become unattributable to a specific passenger — a trade-off I judged acceptable given how rarely that level of detail is queried compared to how often revenue totals are.
